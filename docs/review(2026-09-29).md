# Assistant-readiness review — 2026-09-29

Implementation follow-up: the four findings below are addressed by the policy, diagnostics, memory, and run-lifecycle changes documented in [ASSISTANT_READINESS.md](ASSISTANT_READINESS.md). The original review/evidence is preserved as a historical snapshot; calendar/email remain future features.

Reviewed `main` at `6e260f7`. Static source review; no application code changed and no live provider, mailbox, or desktop sessions exercised. This is a focused review of assistant workflows, not an exhaustive security audit. Calendar and email are proposed features, not defects merely because they are absent. Frontend production build and TypeScript lint passed; behavioral acceptance tests below are recommendations, not tests performed during this review.

## Processes traced

- **Chat:** `frontend/src/app/chatSend.ts` → `ipcClient.ts` → Rust IPC → `ChatService` → planning/delegation or direct agent → provider/tool execution → streamed events and SQLite conversation history.
- **Workspace tools:** manifests/enablement → frontend tool host → `invoke_tool` → invoke registry → handlers/services. Direct chat tools have a separate execution path.
- **Automation:** Tasks UI → durable SQLite definitions/approval → manual or 15-second scheduler claim → tool action or Pi-backed Looper → phase settlement, run records, notifications.
- **Memory/context:** Memory UI → upsert/inspection commands → memory manager; separately, agent session history and system-prompt construction.
- **Credentials/data:** API registry → OS-backed secret storage → backend provider requests/child environment; tool events → shared event hub → frontend. Model/runtime and voice service boundaries were inspected for context, not fully audited.

Useful foundations to preserve: backend-owned credentials, credential-free portable exports, explicit task approval, atomic schedule claims, timezone-aware recurrence, and Pi completion requiring `agent_settled`. A wholesale rewrite is not justified.

## 1. Direct chat tool execution lacks the constraints applied to Pi automation

**Priority: high; address before exposing external content to an assistant with write/shell tools.**

**Evidence:** `src-tauri/src/app/chat_service.rs` binds raw file and Bash tools in `bind_files_tools`/`bind_terminal_tools`. `agent/src/turn.rs` calls `tool.execute(...)` directly. `agent/src/tools/read.rs` and `write.rs` accept arbitrary paths; `bash.rs` executes arbitrary shell commands without an approval check. `src-tauri/src/agent_tools/notepad.rs` likewise accepts explicit filesystem paths. These paths do not pass through `FilesService`'s root checks or the Arxell Pi policy.

**Why this is a problem:** workspace enablement and keyword-based tool selection choose what the model can see; they do not constrain what a selected tool can do. Planning some requests also does not authorize each subsequent action. Direct chat can therefore read outside the intended workspace, overwrite files, or execute commands without the safeguards present in delegated runs. A read-only email connector would not make the *whole assistant* read-only: hostile message content could influence other enabled tools. This is a risk demonstrated by the execution path, not a claim that an exploit was tested.

**Keep vs. improve:** direct tools are fast and convenient for trusted coding requests. Preserve that UX, but introduce a backend action-policy gateway shared by direct chat, invoke handlers, and scheduled actions. Enforce canonical resource scope and explicit grants there; don't use model-selected risk labels as authorization. For initial mail/calendar reading, expose only narrowly scoped read capabilities and withhold shell/file-write capabilities from that processing path. Treat retrieved content as untrusted data, never as approval.

**Trade-off:** centralized authorization adds policy plumbing and occasional prompts, but removes inconsistent safety boundaries. It is not an OS sandbox; stronger isolation is needed if arbitrary shell execution must remain available while processing untrusted content.

**Acceptance:** test out-of-scope paths, symlinks, denied writes, and injected mail/calendar instructions across direct and scheduled execution—not only Pi.

## 2. Sensitive tool details reach shared diagnostic events

**Priority: high; close before handling mailbox content or connector tokens.**

**Evidence:** `ChatService::request_agent_response` copies `ToolEnd.display` and `ToolResult.display` into `chat.agent.tool.*` events. Bash's call display is the raw command, and its result display contains stdout/stderr. `src-tauri/src/observability.rs::redact_payload` replaces only five exact top-level keys; it neither traverses nested objects nor removes secrets embedded in strings. The hub retains up to 2,000 events and broadcasts them to subscribers.

**Why this is a problem:** a command containing a credential, or output containing private data, survives as `display`. Bounding the number of events does not make their contents safe. The Pi metadata policy is stronger, but it does not cover this direct-chat path. There is no evidence here of telemetry or remote log upload; the confirmed exposure is to local event history and subscribers.

**Keep vs. improve:** full displays make troubleshooting easy. Replace diagnostic displays with allowlisted metadata: tool/action identifiers, outcome, counts, duration, and correlation. Keep user-requested content in a separate, deliberate presentation channel rather than general diagnostic history. Add recursive, case-aware redaction as defense in depth, not as a substitute for avoiding sensitive payloads.

**Trade-off:** metadata-only diagnostics lose some debugging detail. Explicit opt-in, short-lived local debug capture is preferable to retaining raw data by default.

**Acceptance:** synthetic tokens in command strings, nested fields, and tool output must not appear in diagnostic events. Mail bodies, attachment contents, and calendar descriptions should have the same exclusion by default.

## 3. “Persistent” memory is volatile, and context inspection overstates what is sent

**Priority: medium; necessary for a dependable personal assistant.**

**Evidence:** `src-tauri/src/app/mod.rs` constructs `InMemoryMemoryManager`; `src-tauri/src/memory/mod.rs` stores entries only in a process-local map. Memory/custom-item upserts return success without durable storage. Separately, `ChatService::inspect_agent_context` lists custom context as `default`/`always`, while actual `request_agent_response` constructs the agent from conversation history and routing hints. `agent/src/agent.rs::build_system_prompt` uses the configured base prompt, filesystem skills, time, and working directory—not these custom memory entries. No memory retrieval tool is bound in `agent_tool_bindings`.

**Why this is a problem:** a saved fact or directive disappears on restart, and adding custom context does not make it part of the direct agent's actual request despite the inspector's loading labels. Preferences such as working hours or summarization instructions cannot reliably guide assistance. This finding concerns Memory/custom context, not SQLite conversation history or the separately persisted base system prompt.

**Keep vs. improve:** the current map is simple and avoids retaining personal data indefinitely. Add a small durable memory repository with explicit user-approved entries, scope, provenance, and deletion. Use one context builder for both real requests and inspection; distinguish available, selected, and actually sent material. Do not automatically copy mailbox bodies into long-term memory.

**Trade-off:** persistence improves continuity but creates retention obligations. Start with explicit facts/preferences, not vector search or automatic ingestion, and make deletion/export behavior clear.

**Acceptance:** saved entries survive restart; deleted entries are no longer selected; the inspector matches the request payload. Test with fake personal data and a mock provider.

## 4. Task history records delegation, not the delegated execution's final outcome

**Priority: high for reliable scheduled assistance.**

**Evidence:** `src-tauri/src/tools/invoke/tasks.rs::run_agent_prompt_payload` returns `running` when `looper.start` returns; `run_looper_payload` instead reports `succeeded` on that same kind of launch acknowledgement. Both manual and scheduled callers immediately set `completed_at_ms`, record a notification, and call `advance_next_run_at`, which clears the claim. `TaskAutomationService` has an insert-only run-history path; there is no run update/reconciliation path consuming Looper completion/failure. Looper executes asynchronously and emits its own terminal events.

**Why this is a problem:** an agent-prompt run can remain permanently “running” even after failure or completion; an explicit Looper task can report success before work finishes. Clearing the claim at launch also permits another manual or recurring run while the previous loop is active. Atomic claims correctly protect the launch occurrence, but not the lifetime of delegated work.

**Keep vs. improve:** asynchronous launch keeps the UI and scheduler responsive. Preserve it, but persist a run-to-loop mapping and reconcile terminal outcomes in a backend orchestration service. Only final outcomes should set completion time and completion notifications. Separate occurrence consumption from active-run/overlap policy, and reconcile interrupted runs on startup. Record scheduling/history failures rather than silently ignoring them.

**Trade-off:** this adds lifecycle/recovery logic, but no new scheduler framework is needed. Define whether overlapping occurrences are skipped, queued, or allowed; don't implicitly choose by clearing a launch claim.

**Acceptance:** test launch → success, launch → failure, cancellation, restart recovery, and another due occurrence during an active run. Each occurrence needs truthful history and a deliberate overlap decision.

## Implications for calendar and low-risk email

These are implementation constraints arising from the findings, not additional reported defects:

- **Calendar:** keep event records separate from executable tasks. Events need start/end, all-day semantics, timezone, recurrence exceptions, and stable identity; a task's `nextRunAtMs` is an execution cursor, not a calendar event model. Reuse the existing timezone/recurrence work where semantics match, rather than converting every event into a Pi task. State clearly that the current scheduler runs only while Arxell is running; closed-app reminders need a separate platform design.
- **Email:** start with one provider and backend-owned, revocable, least-privilege read authorization. Allowlist read operations; omit send, draft creation, delete, label changes, and mark-as-read. Verify the chosen provider's scope and endpoint behavior before implementation. Keep tokens out of frontend state, model context, Pi environments, events, and exports. Do not automatically open links, download attachments, or load remote images.
- **Data use:** default to bounded metadata and user-selected messages. Reading a mailbox and sending its contents to a cloud model are separate permissions; show the destination and obtain explicit consent. Keep initial reads local-only unless authorized otherwise. Read-only access prevents mailbox mutation, not data disclosure or prompt injection.

**Recommended order:** action policy and diagnostic privacy → truthful memory/context → delegated-run reconciliation → local calendar → narrowly scoped email reads. Avoid coupling initial calendar/reminder functionality to coding-agent execution.
